# Synko: проверка функций

Ниже перечислены проверки сборки и границы их покрытия.

Регрессия 2.4.4 воспроизведена на 2.4.3: процесс с `--startup --background` и включённым QuietStartup всё равно имел видимое окно. Причина: ApplicationContext.MainForm автоматически показывается внутри Application.Run. Новый тест запускает настоящий основной цикл, проверяет Visible/Shown и отсутствие инициализации WebView до ручного открытия. До исправления тест падает с `Application.Run exposed the background window after the constructor`, после отделения окна от MainForm проходит. Проверка только конструктора и краткий опрос MainWindowHandle были недостаточны из-за начальной прозрачности окна.

В этом же основном цикле проверяется ручная активация, готовность WebView и закрытие окна с сохранением фоновой работы. Smoke-проверка сохраняет снимки самого WebView без принудительного перевода тестового окна поверх рабочего стола; снимки нативной рамки по-прежнему доступны в `--preview-ui`.

В 2.4.3 проверяются явный `--startup --background` в Run, обновление этой команды при переключении тихого режима и нативная регистрация через RegisterApplicationRestart/GetApplicationRestartSettings для текущего процесса. Отключение автозапуска удаляет регистрацию восстановления. Проверка интерфейса переключает настройку через настоящий WebView. Проверки моделируют вход запуском зарегистрированной команды и повторного экземпляра; реальную перезагрузку Windows эти проверки не выполняют.

В 2.4.2 проверяются резервный поиск обложек при ошибке/задержке Apple, повтор на том же треке, отмена при пролистывании, кэш альбома после перезапуска и отклонение чужого исполнителя/альбома и неподходящих URL. Медиаданные Spotify в этих проверках являются фикстурами. Нативная UI Automation проверяется на окне с заголовком Helium/YouTube, стандартной и переименованной адресной строкой, а также несовпадающим видео. Это проверка системного интерфейса доступности на тестовом окне, а не запуск установленного Helium.

Живой резервный каталог с принудительным HTTP 503 от Apple вернул обложки Stromae / racine carrée, Tame Impala / The Slow Rush и Creedence Clearwater Revival / Cosmo's Factory за 1,2–2,5 с вместе с проверкой доступности самой картинки. Также проверена доступность URL превью YouTube. Метаданные для замера заданы фикстурами; воспроизведение в настоящем Spotify и отображение на другом аккаунте Discord этим замером не проверяются.

Для 2.4.1 проверены тихий запуск по умолчанию в новом и прежнем профиле, сохранение явного отключения, независимость от включения автозапуска, перенос прежних записей реестра и отсутствие окна при незавершённой настройке. Проверки реестра используют отдельную временную ветку. Проверка готового интерфейса включает переключение «Тихого запуска» через WebView и чтение сохранённой настройки.

## Spotify

35 групп Core и 7 групп Windows-проверок: идентификаторы обычного/Store-клиента, выбор Spotify в «Авто» и отдельном режиме, сохранение нового режима без изменения прежних значений настроек, пауза, смена источника, поздняя обложка предыдущего трека, нативная картинка, общий кэш обложек и Spotify-ссылки. Случаи Spotify используют тестовые медиаснимки.

Интерфейс Spotify, иконка, информационная плашка и фильтр проверяются в светлой/тёмной теме при 100%/150% DPI. Все четыре режима источника проверяются на переносы и переполнение. Готовый exe проверяется через `--smoke-ui`, включая сохранение режима Spotify.

Реальный Discord подтвердил тестовую активность `name: Spotify`, `type: 2`, публичную обложку и снятие активности. Отчёт помечен `simulated: true`: данные воспроизведения тестовые. Spotify на проверочной машине не установлен, запуск настоящего Spotify и получение его настоящей медиасессии не проверены. Реальный поиск обложки проверен на метаданных Spotify-фикстуры через каталог Apple.

Поддерживается настольный Spotify для Windows, передающий медиасессию Windows. Используется [системный SourceAppUserModelId](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssession.sourceappusermodelid) и [системная Thumbnail](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionmediaproperties.thumbnail), вход в Spotify Web API не выполняется.

В 2.3 проверены полупрозрачные статусы источников по двум сторонам: раздельные название/состояние, отсутствие роли кнопки и клавиатурного фокуса, попадание в границы окна. Пиксельная проверка canvas на 0%, 50% и 100% воспроизведения обнаруживает лишние высокие маркеры. Проверки проходят в светлой и тёмной теме на 100% и 150% DPI. Автоматическое снижение анимации и контрастные режимы сохранены.

Для обложек добавлены проверки восстановления после HTTP 503 и 429/Retry-After, кэша альбома после перезапуска, изоляции разных исполнителей, повторной загрузки той же картинки, мгновенной нативной обложки Windows и отмены устаревшей загрузки при смене трека. Core: 30 групп, Windows: 6 групп.

Apple Music на этой машине передавал `image/jpeg,image/jpe,image/jpg` для JPEG. Формат нативной картинки теперь определяется по сигнатуре; тест проверяет канонический data URL и фактическое декодирование изображения.

Замер 2.2.1 на текущем Apple Music «Killswitch»: чтение медиасессии с нативной обложкой 310 мс, поиск каталога 985 мс, с загрузкой картинки суммарно 2 006 мс. Повторный отдельный запуск: 370 мс суммарно. Это замер одного трека и текущей сети, не гарантия задержки Apple/Discord. Готовый exe прошёл `--smoke-ui` с `success: true`, включая проверку реального декодирования обложки WebView. После запуска установленного Discord проверены настоящие SET_ACTIVITY, ссылка обложки Apple в ответе клиента и снятие активности; ACK получен менее чем за секунду. Ошибки и ответы RPC также проверены автоматическими тестами.

## Живые проверки на этом компьютере

- Windows видит Apple Music и Chrome; в режиме «Авто» выбирается играющий Chrome
- Фоновая вкладка YouTube распознаётся с суффиксом «воспроизводится аудио»
- Системные обложки доступны от обеих медиасессий
- Чтение адресной строки активной вкладки получает правильный YouTube ID
- Настольный Discord подтвердил тип `Watching`, имя «видео на YouTube», публичное превью текущего ролика и последующее снятие тестовой активности

Проверка опубликованного exe, скриншоты и измерение размера записываются в локальную папку `artifacts`. Эти диагностические файлы и пользовательские профили не включаются в Git.

## Ограничения проверки

Chrome проверен на настоящем текущем видео. Остальные браузеры проверены по классификации, иконкам и общему Windows Media API; отдельный ручной прогон во всех 15 установленных браузерах не выполнялся.

Поведение уменьшенной анимации, скрытия и переключения темы проверяется через интерфейс приложения и его окружение. Физическое переключение всех настроек Windows и длительная работа в фоне в течение нескольких суток не проверены.

Работа загрузчика обновлений и замены файлов проверена локально. Проверка своего GitHub-репозитория до публикации должна вернуть «Релизы ещё не опубликованы». Настоящее обновление между двумя публичными версиями можно проверить после одобрения публикации.

Для Discord нужен URL ролика: нативная картинка Windows сама по себе не является публичным URL. Если видео стало фоновым до запуска Synko, откройте его вкладку один раз. Synko не выбирает вкладки автоматически; только диагностический `--diagnose-address` может кратко выбрать текущую медиавкладку и восстановить прежнюю для проверки адреса.

## Основания решений

В коротких статусах название и состояние разделены промежутком, без длинного тире или точки. Это визуальное разделение двух подписей; общие рекомендации по пунктуации UI: [Microsoft Style Guide](https://learn.microsoft.com/en-us/style-guide/punctuation/colons).

Размер уменьшен удалением WPF-зависимости, подмножеством шрифта и [сжатием single-file .NET](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview#compress-assemblies-in-single-file-apps). Trimming WinForms не используется из-за [официальных ограничений совместимости](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities).

SHA-256 обновления берётся из `assets[].digest` [GitHub Releases API](https://docs.github.com/en/rest/releases/releases). Структура двуязычного README подготовлена по примеру [Win10ray](https://github.com/zephrx0/Win10ray); текст описывает функции Synko.

## Повторение

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Test
Start-Process .\artifacts\Synko-win-x64\Synko.exe -ArgumentList '--smoke-ui', "$PWD\artifacts\production-check" -Wait
Start-Process .\artifacts\Synko-win-x64\Synko.exe -ArgumentList '--preview-ui', "$PWD\artifacts\screenshots" -Wait
```

Отчёт `production-checks.json` должен содержать `success: true`. Для проверки реального Discord при запущенном клиенте:

```powershell
Start-Process .\artifacts\Synko-win-x64\Synko.exe -ArgumentList '--diagnose-address', "$PWD\artifacts\live.json" -Wait
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-live-discord.ps1 -Report artifacts\live.json -Output artifacts\discord-check.json
```
