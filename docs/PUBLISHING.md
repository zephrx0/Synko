# Публикация Synko

Репозиторий: `zephrx0/Synko`. Перед публикацией следует проверить готовую сборку, её контрольные суммы и разрешение владельца на выпуск текущей версии.

## Проверка перед публикацией

1. Выполнить `build.ps1 -Test` и проверить опубликованный exe через `--smoke-ui`.
2. Просмотреть скриншоты и `docs/TESTING.md`.
3. Получить подтверждение пользователя на публикацию текущей версии. Проверить аккаунт GitHub: `zephrx0` (имя профиля `zephyr`).
4. Явно задать локальные `user.name=zephyr` и `user.email=134763007+zephrx0@users.noreply.github.com`, проверить автора и коммитера. Загрузить исходники и дождаться успешной сборки GitHub Actions.
5. Создать сразу опубликованный стабильный релиз с нужным тегом (`draft: false`, `prerelease: false`) и загрузить заранее проверенные файлы. Черновики, в том числе временные, не создавать.

## Файлы релиза

- `Synko-win-x64.zip`: Synko.exe, инструкция и лицензии
- `Synko-2.4.0-win-x64.exe`: тот же автономный exe с версией в названии
- `Synko-2.4.0-win-x64.sha256`: SHA-256 exe

Превью и скриншоты не прикладываются к релизу и не встраиваются в его описание. Фотография владельца остаётся в README репозитория.

Основная ссылка в README ведёт на ZIP. Отдельный exe нужен в том числе для встроенного обновления. Он не требует скачивания отдельного runtime .NET.

## Протокол обновления

Приложение запрашивает `GET https://api.github.com/repos/zephrx0/Synko/releases/latest`. Принимается только стабильный опубликованный релиз новее установленной версии. Ожидается файл `Synko-X.Y.Z-win-x64.exe`, состояние `uploaded` и `digest` формата `sha256:...`, предоставленный GitHub Releases API. URL должен принадлежать этому же репозиторию GitHub.

Загрузка идёт в `%LOCALAPPDATA%\NowPlaying\updates`. Сначала проверяются размер, SHA-256 и версия PE-файла. Только затем запускается отдельная копия текущего exe в режиме установщика, основной процесс завершает Discord RPC и закрывается. Установщик ждёт именно этот PID и время его запуска, сохраняет предыдущий exe, заменяет файл и запускает Synko. При ошибке замены предыдущий файл сохраняется/восстанавливается, журнал остаётся в папке обновления. Пользовательские настройки не заменяются.

До первого опубликованного релиза кнопка проверки показывает «Релизы ещё не опубликованы». Это ожидаемое состояние подготовки, а не сообщение об успешной загрузке обновления. После публикации необходимо отдельно проверить загрузку из настоящего GitHub Releases на второй версии; локальные тесты проверяют протокол, хеши и замену файлов без публикации.

Workflow `build.yml` имеет только права чтения репозитория и выгружает артефакты сборки. Он не создаёт публичных релизов автоматически.
